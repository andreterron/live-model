# Message debugger

Status: first exploratory slice, 2026-08-02.

## Goal

Add a visual, local-only environment for understanding how protocol messages and
operations move between two Live Model machines. The first version should be
useful without a running API or WebSocket server and should keep its history for
the lifetime of the page.

## Decisions

- The website-local debugger records operation knowledge separately from message
  and operation history. Every operation adds one `created` step for its source
  machine and one `received` step for its target. The UI timeline scrubs those
  single-machine steps, so an operation appears only on Client A at time 1 and
  on both clients at time 2. `operationKnowledgeSteps` and
  `operationKnowledgeAtStep()` remain internal to the website debugger.

- The v2 details inspector is a sticky grid column on desktop, allowing the
  sequence view to resize without being covered. It remains a modal bottom
  sheet on mobile. The composer reserves its final row for the compact direction
  control and Send button.

- `/debugger` is the device-sequence v2 UI, while the previous full debugger is
  preserved at `/debugger/v1`. Events and operations each receive their own
  stable letter sequence (`A` through `Z`, then `AA`, `BB`, and so on), and the
  same record keeps its letter in every client column. Selection stays local
  while history is in memory and opens a desktop side panel or mobile sheet.

- Message composition lives in one card above the two client state cards. A
  full-width Client A/Client B direction control flips the source and target by
  rotating its arrow; the machine cards are read-only views of local state.

- The website dev server marks all responses `Cache-Control: no-store` and
  assigns the compiled `live-model` and explorer workspace entries a cache-bust
  query. Vite was serving the mutable, unversioned `packages/*/dist/index.js`
  URLs with `max-age=14400`; Android Chrome therefore kept the old debugger
  class and its old React optimizer import even after an app restart and normal
  refresh. This continues to resolve the workspace packages to their compiled
  `dist` output, not their source trees.

- `terron-ai-tunnel` now rewrites an upgraded WebSocket request's upstream
  `Host` header to `127.0.0.1:<assigned-port>` while preserving the public host
  in `X-Forwarded-Host`. Vite rejected HMR upgrades with HTTP 400 when the
  upstream `Host` remained `live-model.terron.ai`; normal HTTP and application
  WebSocket traffic still worked, which left existing browser tabs silently
  stale. A tunnel regression test now covers the upstream and forwarded hosts.

- The website's Vite dependency optimizer explicitly scans every website route
  and the linked explorer source tree before serving the first page, while React
  runtime entries remain pinned in `optimizeDeps.include`. A long-lived tunneled
  tab therefore does not expand the optimizer generation merely by visiting a
  new route, but other dependencies can still be pre-bundled normally. The
  previous `noDiscovery` workaround exposed ESM barrel modules directly; Lucide's
  barrel caused the browser to request its full icon graph. Lucide imports now
  target individual ESM icon modules so only icons used by a route enter its
  browser graph.

- The website route is `/debugger`, with a route layout and index page so later
  debugger views can be nested beneath it.
- The shared website header names the existing sample screen **State**, the
  existing data browser **Explorer**, and the new screen **Message debugger**.
- The header keeps inline links at desktop widths and collapses them into an
  accessible, auto-closing menu on smaller screens.
- The simulation lives in the website package because it exists only to support
  this exploratory UI. It uses public `live-model` primitives rather than adding
  debugger-specific exports to the library package.
- A machine is a small in-memory `BackendLiveModel` with its own storage. Sending
  an operation records the outbound operation, applies it to the target, and
  records status and state responses. Subscribe and unsubscribe messages are
  also represented.
- Timeline event IDs and sequence numbers are generated by the simulator. They
  are debugger metadata, not additions to the wire protocol.
- The UI owns one simulator instance in React memory. Refreshing or navigating
  away can discard its state, as requested.
- Values accept JSON when valid and fall back to plain text. This keeps the first
  UI quick to use while allowing object and primitive examples.
- Custom operation names can be sent even though the default backend rejects
  them. Showing that rejection is useful for exploring operation handling.
- Protocol messages are grouped into one chronological log per machine. Each
  copy is labeled sent or received because the same wire message is known from a
  different direction at each endpoint.
- Operations have a separate ledger from protocol messages. Both their source
  and target are considered to know an operation once it is sent, and each
  record captures the target state before and after application plus its result.
- The operation timeline scrubber uses operation count as its first time axis:
  zero is before any operation and each subsequent stop reconstructs machine
  state after that operation. This is intentionally linear until time branching
  and causal dependencies exist.

## Uncertainties and follow-up

- **Time branching:** the protocol has no branch/time identity yet. The first
  version uses one linear, local timeline.
- **Conflict hook:** there is no hook that determines whether two operations
  conflict and require automatic time branching.
- **Acceptance hook:** `OperationSetRegistry` determines which operations are
  accepted and how they affect materialized state. Authorization remains a
  separate future policy hook.
- **Dependencies:** protocol `Message` mentions dependencies only as a TODO.
  Timeline sequence communicates observation order, but causal dependencies are
  not modeled or visualized yet.
- The production WebSocket path currently does not return successful operation
  status messages to clients. The simulator deliberately records the synchronous
  `BackendLiveModel.processOperation` result to make both success and rejection
  inspectable.
- The two default roles are Client A and Server B. The simulator itself accepts
  arbitrary labels and roles, so a later UI can switch to client/client without
  changing the model.

## Live Model integration

- The debugger uses the public `BackendLiveModel`, `StorageAdapter`, protocol
  messages, and state types. No debugger classes or types are exported by the
  `live-model` package.
- The in-memory debugger exposes an API version. The website replaces preserved
  instances from older API versions during Fast Refresh, accepting loss of local
  debugger history instead of letting refreshed UI call missing runtime methods.
- No changes were made to the production protocol or WebSocket behavior.

## Local serving

- Terron AI Tunnel discovers the ignored root `subserve.json`, then runs the
  `apps/website` package as an on-demand `node-react` app.
- The website Vite server reads `PORT` when the tunnel provides it and otherwise
  retains port 4200 for ordinary local development.
- Subserve runs the root `pnpm dev` command so Nx starts the website alongside
  package watch builds. The website continues to consume normal compiled package
  entries rather than using development-only source aliases.
- The Subserve app is always-on because it owns a persistent workspace watch
  graph; this also avoids on-demand idle checks racing a long-lived manual start.
- Website development does not wait for redundant dependency build targets;
  root `pnpm dev` already runs those watch builds concurrently. This lets the
  website bind Subserve's port within Terron's readiness window.
- The backend dev target uses port 3001 by default, independently of Subserve's
  injected `PORT`, so the root workspace command can reserve `PORT` for the
  website. `LIVE_MODEL_SERVER_PORT` can override the backend during development;
  the production server still reads `PORT` normally.
- Vite explicitly deduplicates `react` and `react-dom`. This keeps hooks imported
  through the compiled, linked `live-model` package on the same React instance as
  the website renderer and avoids invalid hook calls after dependency reoptimization.
